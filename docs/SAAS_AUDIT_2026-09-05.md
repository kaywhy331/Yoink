# Yoink functional and SaaS experience audit

Implementation progress and verification are tracked in the [fix receipt](SAAS_FIXES_2026-09-05.md).

Audited 2026-09-05 against the **current working tree, version 1.22.6**, including its pre-existing uncommitted changes. This is an audit and implementation backlog; it does not claim that the findings have been fixed.

**Verdict:** Yoink has a substantial commerce engine, explicit action boundaries, extensive automated coverage, and an increasingly coherent interface. It is not yet a polished, self-service production SaaS. The largest gaps are incomplete setup and recovery journeys, inconsistent state presentation, incomplete access to larger collections, and production services that remain outside the active runtime. A visual redesign alone would leave these problems intact.

## Scope and evidence

The review covered the shopper dashboard, admin console, Chrome popup and settings implementation, API and repository boundaries, source ingestion, four store adapters, documentation, and operational workflows. Browser work used a new database at `/tmp/yoink-saas-audit-20260905` and an isolated server on port 33991. Fixtures included 206 products and 205 plans before subsequent UI exercises. No real store cart, external notification destination, or production account was changed.

Evidence labels used below:

- **R — Reproduced:** observed in the isolated app in Chrome.
- **C — Code:** verified in current implementation, without claiming a live external-system exercise.
- **D — Documented gate:** explicitly unfinished or deployment-dependent in the repository and consistent with active code.
- **U — UX assessment:** an improvement justified by the inspected workflow; not a claim that a safety invariant is broken.

Priorities: **P0** blocks a production, multi-tenant SaaS launch; **P1** breaks a journey, loses user work, or misrepresents consequential state; **P2** creates recurring friction or weakens scale, accessibility, and recovery; **P3** improves polish. P0 here does not mean an exploitable security vulnerability was found.

This is a comprehensive review of the implemented product surfaces and major workflow entry points, not a proof that every internal function is defect-free. Hosted identity, managed extension distribution, actual retailer sessions, production notification delivery, assistive-technology use, and real-user performance require separate acceptance runs. Existing tests and code inspection provide evidence for those boundaries, not a substitute for those runs.

The earlier [UX action plan](UX_ACTION_PLAN.md) was consulted, then checked against current behavior. Existing history navigation, server-side product filtering, custom confirmations, user headers, plan pause controls, over-cap reporting, and drop authoring improvements were not treated as missing simply because an older review discussed them.

Making setup easier must not silently activate a store lane or relax these checks.

## Recommended delivery sequence

1. **Restore dependable behavior:** fix YS-16–19, 21, 23–24, 40–42, and 45. Correct the privacy disclosure in YS-47 alongside this work. These are concrete defects or trust gaps that do not require a broad redesign.
2. **Finish activation:** deliver a connected product → plan → Chrome → source → store-check → ready journey. Close YS-06–15 and make notification setup, product review, and source setup reach a verified result.
3. **Make ongoing use efficient:** finish collection management, setup impact review, correction workflows, watch history, contextual support, and analytics drill-through. Address measured DOM/payload costs with representative data.
4. **Complete production operations:** close YS-01–05 and 38–39 against a deployed staging environment with real identity and service boundaries. Run controlled extension/store acceptance, disaster recovery, and operational response exercises.
5. **Validate the experience:** establish real-browser regression gates and observe new users completing the core journeys. Apply visual and copy refinement to demonstrated friction instead of moving the same unfinished workflows into a new layout.

Suggested acceptance targets, to be validated with real users and deployment measurements: a useful first saved plan within two minutes after prerequisites; no silently inaccessible saved records; every blocker names a next action or owner; no lost draft or selection on refresh; all critical dialogs usable by keyboard/screen reader; reload/back/forward preserve task context; field p75 LCP below 2.5 seconds and INP below 200 ms on supported devices; zero unintended retailer mutations during failure/recovery drills. These are proposed product gates, not measured production results.

The intended everyday flow is: **Choose a product → save explicit limits → see exactly what is ready → receive a useful call → let qualified Chrome verify/add → finish checkout → record or correct the outcome.** Operator work should resolve the exceptional dependencies behind that flow without requiring shoppers to understand the commerce engine.
