**What is working and what the measurements establish**

The browser requires fresh proof of the exact item, authorized quantity, first-party seller, and price before declaring cart success. Independent cart verification preserves existing cart quantities. Keep those checks while improving speed; an Add click alone is insufficient. See [completeVerifiedCart](../apps/extension/background.js) at line 7836.

The latest 100 recorded jobs span October 3–14 and include multiple releases. Seventeen have confirmed cart results: 16 Amazon and one Target. Job creation to the recorded confirmation ranges from 8.293 to 13.984 seconds, with a median of 12.346 seconds. These are successful-job measurements, not a success rate or a four-store benchmark. The latest v1.30.43 Amazon success took 11.642 seconds; its browser timing recorded 1.828 seconds to the baseline, 4.253 seconds from baseline to offer verification, and 4.231 seconds from click to cart proof. Source publication to detection and phone display are not established by these measurements.

REDPC has zero configured external alert destinations. Its 52 plans contain 17 automatic cart plans and 35 notification plans, including two needing a target. Notification plans should retain their chosen behavior. Make this distinction obvious when a user expects automatic cart preparation.

Neither platform is established here as faster on a real phone. Let users opt into both and dispatch independently at the same time. A successful API response is not proof of a visible phone notification. Test with the phone locked, on cellular, and while the PC messaging app is active. Server/channel mute and notification settings matter; include a short setup check. [Discord notification settings](https://discord.com/blog/how-to-manage-your-discord-desktop-notifications).

For a local installation, Discord can send outbound HTTPS directly. A locally owned Telegram bot can send directly and receive pairing commands through long polling; opening the PC's API to the internet is unnecessary. Only one receiver should consume a given bot's updates. For a polished shared Yoink bot across many installations, use a small hosted pairing/delivery service that holds the shared bot credential, with per-installation authentication. Never embed a shared bot token in the distributed extension or desktop package. [Telegram API requests and updates](https://core.telegram.org/bots/api#getupdates).

**Fast delivery sequence**

1. The browser proves the authorized cart result and persists enough evidence to recover a reporting interruption without another Add click.
2. Publish the local handoff immediately. Independently commit the server cart event and its external delivery records in one transaction; wake the dedicated dispatcher after commit.
3. Send to each opted-in destination concurrently, within provider limits. Do not wait for an image, link preview, maintenance cycle, another destination, or checkout-page navigation before sending an accurate cart alert.
4. Store provider message IDs and actual attempt/response timestamps. Track queued, sending, provider accepted, retrying, expired, and acknowledged separately. A timeout after acceptance is an uncertain outcome; arbitrary repeated POSTs do not guarantee exactly-once delivery.
5. Before retrying, check opt-in, current outcome, and proof age. Use a short initial retry for transient network failures; provider `Retry-After` takes precedence. A proposed initial alert freshness limit is 60 seconds from proof, after which revalidation or an explicitly dated status is needed. Do not extend the freshness of the proof merely by retrying.
6. Update the existing message when checkout needs attention or a later outcome is confirmed. An Open cart click is not evidence of purchase. Keep test alerts visibly labeled and separate from real outcomes.

Use per-destination ordering and a deduplication key that includes the user, destination, retailer, cart episode, and event type. Already-carted reminders need an explicit cooldown or user request. Disable future sends immediately on opt-out. Telegram publishes per-chat and broadcast limits; Discord returns retry timing with rate-limit responses. [Telegram limits](https://core.telegram.org/bots/faq#my-bot-is-hitting-limits-how-do-i-avoid-this), [Discord rate limits](https://docs.discord.com/developers/topics/rate-limits#exceeding-a-rate-limit).

Proposed engineering targets are a p95 under 250 ms from durable cart-event commit to beginning delivery, and a p95 under two seconds from cart proof to provider acceptance on the tested deployment. These are acceptance targets, not measured results or phone-delivery guarantees. Measure source receipt, job creation, browser lease, Add click, cart proof, provider acceptance, and user acknowledgment independently. A phone test acknowledgment includes human reaction time and cannot be labeled push transport latency.

Example alert, using illustrative item details:

> Amazon cart verified · 1 × Pokémon Elite Trainer Box
>
> Verified item price $54.99 · Shipping · Checked just now
>
> Open Amazon cart to review and place your order.

The link should use the retailer's tested cart route. Avoid PC-only localhost links or session-bearing checkout URLs in phone messages. The phone must use the same retailer account and the intended browser or app; in-app browsers can have a different login. Show item price separately from any verified final total. Shipping, pickup location, payment/address completion, and changing availability remain checkout conditions; a cart is not a guaranteed reservation. Only say “Checkout ready” after the appropriate page and required conditions are actually verified.

Recommended implementation order:

1. Correct alert scheduling, cart versus checkout wording, stale-event handling, existing-cart classification, latency measurements, and the notification test fixtures.
2. Deliver useful Discord channel alerts with provider receipts, isolated retries, an incoming-reader exclusion, and a phone setup test.
3. Add Telegram private-message pairing and delivery; add Discord DMs if users prefer them to private channels.
4. Finish truthful checkout/account handoff and consistent readiness, then validate all four stores and measure phone results before claiming a delivery-speed target is met.
