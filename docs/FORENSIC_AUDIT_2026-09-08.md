# Yoink forensic audit (2026-09-08)

Product-owner forensic analysis of Yoink 1.28.3 (HEAD 88656a4) at the user level and the admin/server level, followed by a critical review lane. Rendered report: see the artifact link in the session summary. This file is the agent-executable ledger: findings are stable ids; claim work by workstream.

Ten auditors walked every shopper, companion, admin and server surface of Yoink 1.28.3 against the live instance and a scratch instance. A second lane of three reviewers then re-verified the findings, challenged each recommended fix, and re-calibrated the whole list against how Yoink is actually used today. This page is the result after that review.

## Read this first

1. The next deploy will crash-loop the service. Source carries migration 68; the live database and running build are at 67. Applying it copies the 455 MB database before migrating, and the host has about 220 MB free and is shrinking roughly 30 MB a day. Free disk before anything else: the 3.0 GB of Playwright browser builds under ~/.cache/ms-playwright (left by earlier audit sessions; keep one Chromium), the ~575 MB of database copies the retention rule can never prune (after-v66, before-legacy-transition, the odd-named ones), and the 372 MB of Windows capture build output. None of this was touched by the audit; it is the owner's call. (P-01, P-02, Z-07)
2. The running service is not the code you are evaluating. The process started Sep 6 17:31 from a build older than the 23:37 rebuild; the two Sep 7 commits (products across stores, pause and resume from the companion) are in neither the running API nor the packaged companion. Health says 1.28.3 for all of them. Rebuild, restart and re-package once disk is freed, in that order. (R-01)
3. Nothing has ever been delivered, and the reason is the companion, not the server. Thirty days of request telemetry show 53,561 heartbeats and zero calls to the notification or job lease routes. Every one of the 148 notifications expired with zero attempts because nobody asked. This also means no add-to-cart job has ever been leased in the field. Confirmation takes ten minutes in the companion's service-worker console on the owner's Chrome; the steps are in finding X-01. (E-01, X-01)
4. A stray npm run dev already migrated the live database under the running service once (the before-v67 backup at 23:36 while the unit ran since 17:31). Do not run it on this host until the data-directory lock lands. (P-04)

## Verdict

Verdict.
Yoink's engine, safety boundary and repository layer are careful and well tested, and the last two fix passes closed most of what the 2026-09-05 audit found on the dashboards.
But measured by the one journey it exists for, the product has never worked in the field: the only source has been silent since Aug 29 while every surface says connected; the paired companion has never polled for a call or a job; two thirds of the owner's plans are stuck notify-only because their cart setup needs an MSRP the catalog does not carry; and the host is days from a full disk with a pending migration that cannot run.
The interface repeatedly asserts states it holds no receipt for: Calls live, Notifications are ready, Ready for activation, running, 1.28.3.The critical review confirmed every critical and most majors, found none that were not gaps, corrected five severities down and three up, collapsed the list to 176 distinct problems, retargeted the biggest fix from the server to the companion, and replaced item-by-item fixing with ten mechanism-sized workstreams plus one manual week of operational recovery.
The best approach is not to work the list top to bottom.
It is to make four journeys green in order, each defined by receipts the API already has: the host survives a deploy; a call arrives and the owner is told; a qualified store adds one to the cart; every status word carries the query that justifies it.

## What the critical review changed

- Root cause retargeted (E-01, X-01). Auditors C, E, R, A and F filed the 148 expired notifications as a delivery failure and blamed the two-minute window. Reviewer X exercised the server lease route on the scratch instance (sound), then read the live instance's 30-day telemetry: 159,699 requests, zero to the notification or job lease routes. The companion never asks. The product fix (a delivery-health line on Home, Insights, Settings and admin) stands; the engineering fix moves to the companion's gated poll loops plus a per-device last-poll timestamp, an honest no_device_poll failure code and an operator alert. Lengthening the window, which two auditors rejected and one considered, would not have helped.
- Severities corrected. Down: B-01 (shopper is told one step late, not blocked), B-02 (brand half is a stale-build artefact that HEAD already backfills), D-01 (manual update works and is documented), F-01 (one principal locally, so nothing wrong is shown today), P-02 (about 575 MB unreachable, not 1.1 GB), plus C-02, G-01, G-02, Q-09, F-13, D-09, P-10, E-06, E-12, P-11 on product-owner judgement. Up: C-05 (it is the plan-side reason zero cart adds exist), P-01 reworded to fire on the next deploy. Result: 17 criticals became 9 distinct.
- Duplicates collapsed. Fifteen clusters where two to nine auditors filed the same fact: stale runtime (R-01), undelivered notifications (E-01), catalog counted five ways (R-07), validation errors as HTTP 500 (R-04), time formatting (Q-04), silent source (E-03), resume without confirmation (A-03), pause reason invisible (A-12), silent notify-only downgrade (C-05), disk (P-01), outbox (R-03), dead worker (G-07), revoked devices (A-17), first-plan seed (C-02). Twenty-one rows now point at a canonical id.
- Fixes replaced by mechanisms (reviewer Y). Four architectural facts the auditors under-weighted: every engine rule has a PostgreSQL twin in postgres-signal-*-apply.ts, so engine fixes are M not S; the table count is sealed at 105 and no finding needs a new table; typed error mapping already exists and only the fallback masks to 500; the paused-and-deleted-plans bug is one missing status predicate, and an un-delete path already exists. Y agreed with most fixes but replaced several: capability chips computed in three clients become one API-served capability per store; the first auto-created plan reuses the existing safe draft instead of a new branch; MSRP backfill is dropped in favour of a fixed-cap default setup; brand inference is dropped; analytics bars use <meter> rather than a class ladder; backup UI is S–M because VACUUM INTO is already an online copy; the non-looping exit code only works with a persistent unit file.
- Would not build. A copy-annotation lint, a second tenant pause flag, typed-phrase deletion, an outbox 'deliver now' with no consumer, an in-app selector editor, a manifest update_url (Chrome ignores it for unpacked extensions), a local admin PIN, a bottom nav, an MSRP backfill nobody has shown the source can feed.
- Framing challenged (reviewer Z). The audit measured a single-operator loopback install against a stranger-shopper SaaS bar, so about 25 rows target surfaces with zero users (drop windows: none ever created; Discord source: disabled; Windows capture: an untracked research probe; admin Users: zero rows; 390 px layouts on a desktop-driven product). Those are logged and deferred, not deleted. Z also walked keyboard order (Home fine, Products needs ~192 Tab stops), confirmed the privacy export works, and added the pipeline-receipt strip (Z-01) and the notify-window question (Z-02) that no auditor asked.
- Risks of acting on the audit as written. Batch schema changes into one migration and free disk first, since every migration copies the database; do not let the server write into Chrome's extension folder without a deliberate decision (D-01); do not add impersonation authority to fix F-01 locally; do not scrape retailer CDNs for images (B-02) since Chrome is the only component that touches stores; keep B-07 a copy change, never a policy change; C-01's deleted-plan fix must record a decision, not silently recreate a plan; one confirmation on resume is enough, not three.

## The ten that matter this month

1. **Free disk, then make the deploy safe** (P-01, P-02, Z-07, P-04, X-07). Nothing else survives a crash loop. Manual cleanup this week, then a free-space preflight before the pre-migration copy, a non-looping exit with a persistent unit, and a data-directory lock so a stray dev process cannot migrate production again.
2. **Stamp the build so drift is visible** (R-01, X-05, P-08). Health must carry commit, build time, start time and schema version, and release:local must assert the restarted process reports the sha it built. Until then every code-based claim, including this audit's, is about a build the owner may not be running.
3. **Find out why the companion never polls** (X-01, E-01). Ten minutes in the service-worker console on the owner's Chrome. Then the server records last poll per device, labels unpolled expiries honestly, and alerts after five silent minutes. Every downstream 'Not delivered' label is wrong until this is known.
4. **Make 'connected' mean something** (E-03, E-14, R-05, X-04). The source has been silent since Aug 29. Age-based staleness from the last registration or delivery, the stored registration failure shown in the connect dialog, and the Amazon readiness rejection that loops every six minutes shown on its store card.
5. **Tell the owner why plans are stuck** (C-05, B-07). Twenty-one of thirty-one plans fell back to notify-only because the only cart setup is MSRP-based and no listing has an MSRP; the card says retry is automatic. Surface the skip reason with a one-click 'Set price cap', and change the default setup to a fixed cap.
6. **Paused and deleted plans must stop** (C-01, C-02, X-06). One missing status predicate lets paused and deleted plans keep generating calls, contradicting three dialogs. Same pass: seed auto-created plans from the existing safe draft so the first plan is not 'legacy, add to cart, no cap'. Both need their PostgreSQL twin.
7. **Show delivery health and the pipeline receipts** (Z-01, A-23, C-11, E-08, X-03). One server-computed object rendered on Home, Insights, Settings, admin Overview and the popup: last signal, last job, last lease, last delivered, last cart-ready, each with an age and a lever. Also label the push's own toast so it stops masking Yoink's absence.
8. **Return real errors instead of masked 500s** (R-04, C-06, P-06). One typed error base class and one instanceof branch turn catalog conflicts and validation into 400/409 with a message, stop the companion's retry loops, and make every other dead end legible.
9. **Say which store can add, before the click** (B-01, B-06, B-11). Capability per store served by the API from the lane registry and readiness, rendered as a chip on the product row and the Stores directory (which today hides seven of the twelve add-capable stores), with marketplace rows not selectable under a first-party policy.
10. **Unblock the admin's evidence and the Best Buy gate** (G-01, G-05). A one-line server fix restores capsule downloads and the fixed-pending-live state on Diagnostics, and the activation gate must read the lane checklist and open incidents so 'Ready' never sits beside two open adapter defects.

## Method

Audit lane. A shared brief fixed ten criteria (guided path, no dead ends, self-service, reversible, consistent, trustworthy, responsive, accessible, discoverable, proactive), three severities, three effort sizes and three evidence bases, and required an alternative approach on every row. Ten auditors ran in parallel, one per surface: A shopper shell and first run, B products and stores, C plans, calls and money, D Chrome companion, E sources and notifications, F admin daily loop, G admin operations and repair, P platform and server, Q cross-cutting patterns, R a field walk of the live instance. Evidence: 78 GET routes against the live API (never a mutation, never the SQLite file), a scratch instance with an empty data directory for every mutation probe, headless Chromium at 1280 and 390 px for A, B, F and R, the service journal, and file-and-line reads of HEAD. Each auditor also re-verified the 2026-09-05 fix receipt for its surface.
Review lane. X (verifier) re-read 68 rows against source and the live instance, exercised the notification lease route on scratch, and read 30 days of operational telemetry to establish the root cause. Y (architect) judged all 124 critical and major fixes against cause versus symptom, the guardrails, the sealed table count and the PostgreSQL twins, and grouped the survivors into mechanisms. Z (devil's advocate) audited coverage, re-measured the field facts, walked keyboard order, challenged eleven severities and the item-by-item framing, and listed the risks of acting on the audit as written.
Limits. No browser extension host on this machine, so companion behaviour is code-based and the poll-loop cause needs the owner's Chrome console. The live database was never opened; schema state was inferred from backup names. Three findings depend on the stale build and are flagged 'deploy fix'. The audit's concurrent load produced one 15-second admin snapshot that reviewer X could not reproduce alone. The audit's own footprint on the full disk was about 40 MB of scratch files, removed at the end; the 3.0 GB of browser builds predate this session.
Artefacts. The ten auditor reports, three review reports, the parsed findings dataset and the build scripts are in the session scratchpad; the agent-executable ledger is docs/FORENSIC_AUDIT_2026-09-08.md in the repository (uncommitted).
